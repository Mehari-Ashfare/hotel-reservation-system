How these folders work together

The application entry and route table connect the folders. A page renders a screen, shared components provide reusable interface pieces, context/hooks provide shared state, and services communicate with the backend.

Entrymain.jsx starts React and loads global styles.
NavigationApp.jsx chooses a page and its layout.
Screenpages/ composes interface components.
Shared logiccontext/ and hooks/ expose app state.
Data and styleservices/ calls the API; assets/ supplies visuals and CSS.
assets/Visual resources

Objective: Keep static resources used by the interface, such as stylesheets and image files.

  • styles/ contains global.css, imported by main.jsx for site-wide styling.
  • images/ exists but is currently empty.

Use this folder for assets that belong to the app source and are imported by components or styles.

components/Reusable interface

Objective: Hold UI building blocks that can be reused across multiple screens.

  • common/ has reusable Button, Input, Modal, StatCard, and a barrel export file.
  • layout/ contains the dashboard frame, header, and sidebar.
  • PaymentModal.jsx is currently directly under components/.

Pages compose these pieces instead of rebuilding the same controls and navigation on every screen.

context/Shared application state

Objective: Make important state available to many components without passing it manually through every layer.

AuthContext.jsx stores the current user and provides login/logout behavior. AuthProvider wraps the app in App.jsx; components can read authentication state with the exported useAuth function.

hooks/Reusable React logic

Objective: Group custom React hooks: functions that let components reuse stateful behavior.

The current useAuth.js re-exports useAuth from AuthContext as a convenient import path. It does not currently define separate authentication logic.

layouts/Page frames

Objective: Provide the outer structure shared by a group of pages.

PublicLayout.jsx supplies a public-site header, content outlet, and footer. App.jsx uses it around the landing page. The authenticated dashboard frame is currently in components/layout/.

pages/Route-level screens

Objective: Organize the screens users visit, grouped by feature or audience.

  • Admin/: staff list and audit logs.
  • Auth/: login, registration, and password reset screens.
  • Dashboard/, Reports/, and Profile/: dashboard and account screens.
  • Guests/, Reservations/, and Rooms/: hotel operations and guest booking screens.
  • Public/ and Staff/: landing page and staff profile.

App.jsx imports these pages and maps URL paths to them.

routes/Currently empty

Possible objective: This folder could hold route configuration if routing is later separated from the main app component.

At present it contains no files. The active React Router setup and path-to-page mapping are in App.jsx; this empty folder is not part of the current runtime flow.

services/Backend communication

Objective: Keep HTTP request logic out of screen components and organize it around application features.

  • api.js creates the shared Axios client and attaches the saved authentication token.
  • Feature services wrap requests for auth, guests, rooms, reservations, payments, reports, dashboard data, staff, and audit logs.

Pages call these services to load or change data through the backend API.

utils/Currently empty

Possible objective: Store small shared helper functions that do not belong to one page or service.

There are currently no files in this folder, so it is not part of the application's current runtime flow.

A practical rule for adding code

Put a screen in pages/, shared visual pieces in components/, backend calls in services/, shared React state in context/, and global visual files in assets/. Keep a helper in utils/ only when it is genuinely shared and does not belong more naturally to a feature service or component.

Guide scope: folders under frontend/src/. The folder explanations describe the current structure, including empty folders.
