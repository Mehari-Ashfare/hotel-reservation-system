Hotel Reservation System · Backend Guide

How the backend works

This guide follows the backend from its npm start command to PostgreSQL and back to the client. The diagrams describe the current project structure and active Express setup.

1. Startup: npm command to listening server

Run these commands from the backend directory. The development command restarts the process when watched files change.

server.js tests the database connection before calling app.listen(). If that check fails, startup reports an error instead of serving requests.

cd backend
npm run dev   # development with nodemon
npm start     # start with Node.js

2. Request: client to database and back

A request passes through app-wide middleware before its route handler. A controller coordinates the operation and produces the HTTP response.

Typical path: route → controller → model → database. In this project, some controllers also call the configured database pool directly, so a model is not always in the path.

3. What happens inside app.js

The order matters: middleware registered earlier gets the request first. The app then mounts route groups and installs the final error handler.

Request setup
  1. CORS rules configure which browser origins may call the API.
  2. Security and performance middleware apply shared protections and response behavior.
  3. HTTP logging and audit logging observe requests.
  4. JSON and URL-encoded parsers read request bodies.
  5. Staff validation runs before route handling.
  6. Swagger documentation is configured outside production.
Mounted API groups
  • /api/auth — registration, login, password reset, current user
  • /api/guests — guest records
  • /api/rooms — rooms and room types
  • /api/reservations — bookings and their status
  • /api/payments — payment operations
  • /api/reports, /api/staff, /api/audit, /api/dashboard

Useful endpoints: /api/health reports health, /api/metrics reports metrics, and /api-docs provides Swagger documentation in non-production mode. Check the route and environment configuration if an endpoint behaves differently.

4. Backend folders and their roles

These are the main pieces involved in the running service, plus nearby database and testing resources.

backend/
├── package.json                 # scripts and dependencies
├── server.js                    # database check, listen, shutdown
├── app.js                       # Express middleware and route mounts
├── .env                         # local configuration (keep private)
├── src/
│   ├── config/                  # database connection and API docs setup
│   ├── routes/                  # URL/method mapping and route middleware
│   ├── controllers/             # request handling and business operations
│   ├── models/                  # database queries and data operations
│   ├── middleware/              # auth, validation, audit, errors, etc.
│   ├── utils/                   # logging, email, and shared helpers
│   └── scripts/                 # backend maintenance scripts
├── database/
│   ├── schema.sql               # database structure
│   ├── seed.js                  # sample data insertion
│   └── clean.js                 # database cleanup utility
└── APITEST/                     # standalone API exercise scripts
Open file responsibilities
  • server.js imports the Express app and database check, waits for the check, then opens the HTTP port.
  • app.js creates the Express app, applies shared middleware, exposes utility endpoints, mounts API routers, and registers error handling.
  • src/routes maps HTTP methods and paths to middleware and controller methods.
  • src/controllers reads request data, applies application rules, invokes data access, and sends status and response data.
  • src/models contains reusable database operations. Some controller files also query the pool directly.
  • src/config/database.js manages the PostgreSQL connection pool and provides connection/query helpers.
  • src/middleware handles cross-cutting request work, including authentication and error processing.
  • database/schema.sql defines tables; database scripts are separate from the server request path.
  • APITEST contains API testing clients, not Express routes mounted by app.js. Root-level legacy files such as roomApi.js are also standalone test clients.

5. Authentication and errors

Protected endpoints

Route middleware can verify a bearer token and check the user’s role before calling the controller. Public routes such as login and password-reset requests do not require an existing login. The exact protections are configured per route.

Failed requests

Async route handlers are commonly wrapped with ErrorMiddleware.asyncHandler. Errors are forwarded to the final error middleware in app.js, which formats the HTTP error response. A route that does not match is handled as a not-found case.
